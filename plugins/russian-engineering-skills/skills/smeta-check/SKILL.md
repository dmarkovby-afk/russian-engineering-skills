# Smeta Check

## Purpose

Use this skill to verify whether an estimator has actually corrected expert remarks and whether a GGE estimate package is complete enough to submit.

Prefer evidence from:

1. Expert remarks (`.doc`, `.docx`, `.pdf`) converted to text.
2. Local package contents (`.gge`, `.xml`, `.xlsx`, archives, КП/прайсы).
3. Machine inspection of GGE/XML files.
4. КПСР/smetafree protocol and completeness check, when available.

Если пользователь открыл SmetaFree или КПСР и проверка нужна для аудита, самостоятельно загружай актуальные рабочие копии, открывай протоколы и выполняй доступные проверки без дополнительного запроса. Запрашивай пользователя только для авторизации, при технической недоступности сервиса или когда требуется решение по неподтверждённым исходным данным.

## Workflow

### 1. Inventory the package

List all files in the estimator folder and classify them:

- `SummaryEstimate` / ССР, ССРСС.
- `LocalEstimateResourceIndexMethod` / ЛСР.
- `QuantityTakeoff` / ВОР.
- КАЦ / конъюнктурный анализ.
- пояснительная записка, сводная смета ПИР, расчеты подключений.
- КП, прайсы, счета, договоры and other justification files.

If filenames or paths contain Cyrillic characters and tools fail, copy files into a temporary ASCII path before parsing. Do not modify originals.

### 2. Extract remarks

For `.pdf` remarks, use the `read-pdf` skill if available. For old `.doc`, use Word COM to save as text when possible.

Turn remarks into a numbered checklist:

- General form and комплектность.
- КАЦ and files of justification.
- ССР/ССРСС remarks.
- Object/local estimate remarks.
- Physical quantities / ВОР / project solution correspondence.
- Items requiring external design documents such as ПОС, ТУ, reports, letters.

Keep exact document numbers, ЛС numbers, resource codes, percentages, and required values.

### 3. Inspect GGE locally

Run the bundled script:

```powershell
python $env:USERPROFILE\.codex\skills\smeta-check\scripts\inspect_gge_package.py "C:\path\to\estimate-folder"
```

The script prints:

- file type/schema for every `.gge`;
- all ССР local-estimate references;
- actual ЛСР numbers present;
- missing ЛСР referenced by ССР;
- QTF/VOR link counts in ЛСР;
- ВОР work counts;
- obvious absence of КА files in the package.

Use the script as a first pass only. Verify critical findings manually in XML or КПСР.

### 4. Check common failure points

Always check these, because they often decide whether a package is truly corrected:

- **Missing ЛСР in ССРСС**: if ССР references `06-01-04` and `06-01-05`, corresponding ЛСР files must exist or ССР must be corrected.
- **ЛСР to ВОР links**: positions should have `QTF`, `FileNameQTF`, and `NumQTF`. Empty QTF means the expert remark about ВОР linkage is not fixed.
- **КАЦ**: if resources use current prices / КП / прайсы, expect a КАЦ GGE/XML and separate justification files linked to positions. A ЛСР alone is not enough.
- **Winter costs**: compare ССР value against the expert-required percent and basis.
- **Construction control**: if omitted, expect a customer letter or other justification.
- **Technological connections**: expect calculations, tariffs, contracts, ТУ, or КАЦ for specialized organizations.
- **ПИР**: expect a separate сводная смета ПИР and supporting recalculations when requested.
- **Project-only checks**: перевозка грунта/мусора by ПОС, physical quantities by ВОР/project drawings, and technical reports cannot be fully verified without those documents.

### 4a. ВОР, проектные объёмы и ресурсы расценок

При проверке соответствия ВОР проекту сначала различай: физический объём работы/конструкции; основной материал или оборудование по проекту; нормативный либо справочный ресурс расценки. Отсутствие последнего отдельной строкой в проектной спецификации и отличие его расхода от объёма конструкции сами по себе не являются ошибкой.

- Прослеживай цепочку «строка ВОР → соответствующая позиция ЛС → расценка и ресурс → проектная база». Используй номер ВОР и позиции, связи QTF и связи ресурсов; учитывай несколько позиций ЛС на одну строку ВОР. Не сопоставляй по порядку строк или одному совпавшему числу.
- Проверяй фактические составы расценок в предоставленной ЛС: расход на измеритель, объём работы, коэффициенты, добавочные/вычитаемые позиции, суммирование ресурсов и округление. Приводи номер ЛС, позицию, код расценки, единицы и проверяемое выражение. Различай м³ и 100 м³, м² и 1000 м², кг и т, штуки и комплекты. Пересчёт комплекта в штуки требует подтверждения состава.
- Численный расход, подтверждённый ресурсной частью ЛС, не нужно повторно искать в проекте. Например, при проектной базе 1,5 м³ и расходе щебня 1,15 результат 1,725 м³ не является расхождением. Однако подтверждение арифметики не доказывает применимость самой нормы, правильность проектной базы или полноту состава работ.
- Нулевой/задаваемый по проекту расход ресурса в норме, отдельно введённый материал, оборачиваемость опалубки или коэффициент без основания не становятся подтверждёнными нормативными расходами только из-за наличия строки в ЛС. Запрашивай расчёт/основание, а не обязательную отдельную строку такого ресурса в проекте. Совпадение количества без смысловой связи не доказывает происхождение ресурса.
- Отдельно проверяй характеристики основных материалов: марку, диаметр, толщину, жёсткость, исполнение и комплектность. Подтверждённый нормативный расход не снимает реального несоответствия выбранного материала проекту. Различие наименования работы в расценке и проекте сначала оценивай как вопрос применимости нормы, не как доказанную замену проектного решения.
- Сверяй актуальные ВОР и ЛС между собой. Если в ЛС материал, единица или объём уже исправлены, а ВОР отстаёт, пиши «ЛС исправлена; требуется синхронизация ВОР», не требуй повторной замены в ЛС. Противоречия самих проектных листов отделяй от ошибок сметчика.
- Проверяй ссылку до содержания страницы: точный файл в заданной папке, физическая страница PDF и, отдельно, номер листа в штампе. Если подтверждение найдено на указанной странице, оставляй ссылку; иначе ищи в актуальном томе и указывай, где искал и где нашёл. Для нормативного ресурса проектная ссылка подтверждает базовую работу, а расход обосновывается ЛС. Не подставляй неподтверждённую страницу для формального закрытия замечания.
- В простой построчной таблице разделяй: «подтверждено проектом», «расход по расценке подтверждён», «расхождение ВОР и ЛС/проекта», «нужно обоснование», «противоречие исходников». Допустимы существующие статусы отчёта, если пояснение явно различает эти случаи. Не представляй все спорные строки как доказанные ошибки; показывай, какие прежние замечания сняты и почему.
- При пересмотре проверяй полное покрытие позиций, в том числе вложенных ресурсов, и соответствие пояснения конкретной строке. Не изменяй количества, формулы или подбор расценок в рамках одной лишь правки ссылок. После разрешённых правок проверяй неизменность остальных данных; сохраняй резервную копию перед перезаписью.

### 4b. ССРСС в Excel: стоимость экспертизы и разные ставки НДС

Если в ССРСС присутствует стоимость экспертизы с отличающейся ставкой НДС, формируй Excel по структуре пользовательского эталона «Сводный сметный расчет.xlsx»:

- Используй восемь основных колонок: номер; обоснование; наименование; строительные работы; монтажные работы; оборудование; прочие затраты; всего. Стоимость экспертизы и относящийся к ней НДС показывай в колонках «Прочие затраты» и «Всего».
- В главе 12 выводи экспертизу отдельной строкой в стоимости без НДС. В обосновании указывай подтверждённые номер, дату и приложение к договору; не подставляй отсутствующие реквизиты.
- После строки экспертизы показывай «Итого по главе 12» и «Итого по главам 1–12». Заголовок главы объединяй по ширине таблицы, а подписи итогов — в колонках обоснования и наименования, как в эталоне.
- В разделе «Налоги и обязательные платежи» основной НДС рассчитывай только от затрат, облагаемых основной ставкой. Стоимость экспертизы с иной ставкой исключай из этой налоговой базы.
- НДС по экспертизе выводи отдельной строкой с фактической ставкой договора. Следующей вспомогательной строкой показывай логику расчёта в виде «ставка % от налоговой базы», отдельно для каждой применённой ставки.
- Для каждой ставки НДС сохраняй отдельную видимую строку и отдельную налоговую базу. Не объединяй разные ставки в одну сумму и не допускай повторного начисления НДС на экспертизу.
- Итог по налогам должен равняться сумме всех строк НДС. Итог по сводному расчёту должен равняться итогу до налогов плюс все строки НДС. Сверяй сумму экспертизы с НДС с полной ценой договора до копейки; в ССРСС в тысячах рублей применяй предусмотренное документом округление.
- Расчётные ячейки Excel по возможности заполняй формулами, а не вручную введёнными итогами. Числовые ячейки оформляй единообразно, обычно с двумя десятичными знаками; нулевые значения можно оставлять пустыми, если так оформлен эталон.
- Сохраняй визуальную иерархию эталона: объединённые заголовки разделов, границы всей таблицы, выделенные строки промежуточных итогов, перенос длинного текста, выравнивание сумм и одинаковые стили строк для однотипных затрат. Не переносить в новый файл проектные значения из эталона — использовать только его структуру и оформление.
- Если договор содержит только цену с НДС, выделяй стоимость без НДС лишь при явно указанной ставке и проверяемой арифметике. При отсутствии подтверждённой ставки или состава цены не рассчитывай её по предположению.
- Перед выдачей Excel выполни контроль: сумма по каждой строке; итоги главы 12; налоговые базы; каждая ставка НДС; общий итог; отсутствие двойного НДС; совпадение с ССРСС/GGE и договором; визуальная проверка объединений, границ, переносов, обрезанного текста и области печати.

### 5. Use КПСР/smetafree when available

If the user has opened smetafree or КПСР:

1. Read the Browser skill before interacting with the in-app browser.
2. Import the package through the site UI. If automation cannot upload files, create short ASCII copies in a temporary folder and ask the user to drag/drop them.
3. Check:
   - import count (`Загружено X из X файлов`);
   - `Протокол` for each ЛСР/ССР/КА/ВОР with nonzero remarks;
   - `Проверка комплектности`;
   - `Проверка обоснований`, if available.
4. Do not rely only on the left monitor counters. Open the protocol rows and quote the error descriptions.

If downloads are unsupported, read visible rows from the modal/table and state that XLSX export could not be downloaded.

### 5a. XSD-ошибки GGE после Госстройсметы и ГРАНД-Сметы

Если SmetaFree показывает «Файл не соответствует схеме», отделяй техническую XSD-ошибку от замечаний ФСНБ и от содержательных вопросов к смете.

- Сначала установи фактическое происхождение файла по `<Meta><Soft>`: программа и версия могут показывать, что файл после работы в Госстройсмета-онлайн был повторно открыт, сохранён или сформирован в ГРАНД-Смете. Это обстоятельство фиксируй как источник возможной несовместимости сериализации, но не объявляй причиной без проверки XML.
- Проверяй именно тот файл, который загружен в SmetaFree: сопоставляй имя файла с внутренними `<Num>`, `<File><Type>`, названием ЛС и датой/версией выгрузки. Не переносите выводы по ЛС 07-01-01 на ЛС 06-01-01 только из-за похожего имени.
- Выполняй локальную проверку по фактической XSD 3.01 и сохраняй все сообщения с указанием элемента, родителя и строки XML. Если локальная схема не найдена, не утверждай точную XML-причину по одному сообщению интерфейса SmetaFree.
- Не объявляй причиной XSD сами по себе: нулевые количества и стоимости, отрицательные корректирующие объёмы, пользовательский код, конъюнктурный ресурс, строки «До 7 см/До 5 см», коэффициент физического объёма или ресурс с нулевым расходом. Сначала проверь их типы и обязательность полей в XSD. Это могут быть отдельные содержательные или ФСНБ-замечания, но не обязательно нарушение схемы.
- Особо проверяй порядок элементов в расширенных типах ресурсов. Для GGE 3.01 `LinkResource` должен находиться в допустимом месте последовательности схемы; в ресурсах с `IsReturnMat`/`IsTurnover` нарушение порядка может дать сообщение «ожидался IsTurnover» даже при полностью читаемом XML.
- `LinkResource` не удаляй для прохождения стороннего XSD-checker, если связи нужны SmetaFree. Сначала исправляй только доказанный порядок/структуру элементов, сохраняя `IDResourceLink`, `IDResource`, количества, цены, формулы, коды и наименования.
- Не меняй сметные решения для устранения XSD без отдельного поручения. Создавай отдельную исправленную копию, сравнивай количество и значения `LinkResource` до/после и повторно валидируй XML локально. Для доказанного нарушения порядка допустима только минимальная перестановка элементов.
- После исправления в SmetaFree сначала удали старую загрузку именно этого файла, затем перезагрузи страницу и загрузи исправленную копию. Повторная загрузка рядом со старой записью не является подтверждением: SmetaFree может показывать старую XSD-ошибку или объединять одинаковые внутренние номера ЛС.
- В итоговом отчёте раздельно указывай: локальный результат XSD; факт принятия файла SmetaFree; число загруженных файлов; результат проверки ФСНБ; число и содержание замечаний после повторной проверки. Если интерфейс показывает только дубликат или не раскрывает строку XSD, называй проверку SmetaFree неподтверждённой, а не успешной.
- В ведомости изменений описывай только доказанное действие: «в исправленной копии изменён порядок элементов `LinkResource` согласно XSD, связи сохранены; выполнена повторная загрузка и проверка в SmetaFree». Не записывай удаление ресурса, изменение нулевого объёма или замену кода, если это отдельно не подтверждено исходными данными и поручением.

### 6. Report format

Answer in practical Russian. Separate:

- **Что исправлено / подтверждено**.
- **Что не исправлено**.
- **Что невозможно проверить по представленному комплекту**.
- **Что надо сделать сметчику**.
- **Можно ли формально загрузить ответ**.

Do not say "исправлено" unless a file/protocol proves it. Use "не подтверждено" when the package lacks supporting documents.

For a report to the estimator, use direct actionable wording:

- "Передать ЛСР 06-01-04 и 06-01-05 либо откорректировать ССРСС."
- "Сформировать КАЦ в GGE/XML и приложить КП/прайсы с привязками."
- "Исправить ссылки для уточненных ресурсов в ЛСР."
- "Повторно проверить комплект в КПСР до передачи."

## Limits

- КПСР validates format and many consistency checks, but not all expert comments.
- Compliance with project quantities requires project documents, ПОС, drawings, ТУ, technical reports, and signed calculations.
- If only estimate files are present, clearly mark project-solution checks as not verifiable.
