# Пояснительные записки

## Workflow

Используй навык для пояснительных записок российской проектной документации, особенно когда замечания требуют добавить сведения из паспортов, технических условий, чертежей, смежных томов или конструктивно идентичного объекта-аналога.

1. Сначала прочитай замечания и преврати их в короткий перечень требований.
2. Проверь крайнюю редакцию ПЗ и для каждого замечания установи: уже устранено, устранено частично или не устранено.
3. Если пользователь просит только сопоставить или предложить изменения, не редактируй файл. Выдай минимальные тексты вставок и места их внесения. Редактируй только после явной команды внести изменения.
4. Изучи структуру ПЗ по страницам: содержание, текстовую часть, приложения и графическую часть.
5. Найди в источниках только факты, необходимые для закрытия конкретных замечаний. Сохраняй ссылки на страницы источников.
6. Сформулируй дополнения в стиле существующей ПЗ: официально, кратко и без описания процесса экспертизы.
7. Редактируй исходный DOCX, если он доступен. Сохраняй результат отдельным файлом с понятным суффиксом; исходник не перезаписывай.
8. Проверь итог извлечением текста и визуальным рендером всех страниц.

## Minimal Source Rule

При использовании котельной или другого объекта-аналога:

- бери только сведения, прямо необходимые для устранения замечаний;
- не переноси попутные технические решения, характеристики и исправления, которых эксперт не запрашивал;
- не расширяй объем ПЗ «на всякий случай»;
- используй проектные значения текущего объекта, если они уже установлены техническими условиями, расчетами или спецификацией;
- при расхождении аналога и текущего проекта не подменяй данные: укажи расхождение и запроси подтверждение только если без него нельзя закрыть замечание;
- отделяй штатный режим от аварийного и не включай аварийные расходы в среднесуточный баланс без прямого основания;
- не называй расчетный расход паспортной производительностью оборудования, если паспорт это не подтверждает.

Для каждого замечания добавляй минимальный достаточный набор: требуемый факт, значение, единицу измерения и место в ПЗ.

## Content Rules

- Add factual information, not commentary about the review process.
- Keep Russian engineering terminology consistent with the source volume.
- Mention that graphical materials are included when the user confirms they are already added.
- If a comment asks for data already present, cite where it appears or add a clarifying sentence only if it improves traceability.
- When equipment characteristics come from a passport, include only the values relevant to the section being corrected.
- Не пытайся закрыть замечание к графической части одной только текстовой вставкой. Отдельно укажи необходимое изменение чертежа.
- Проверяй единицы измерения и арифметику балансов до внесения текста.

## DOCX Editing

- Для раздела АР по умолчанию используй рабочую копию утвержденного пользователем файла `assets/templates/Шаблон_ПЗ_АР_рамка_штамп_утвержденный_2026_08_10.docx`. Считай его эталоном рамок, основной надписи, размеров надписей, колонтитулов, нумерации листов и структуры текстовой части. Этот шаблон принят пользователем после визуальной проверки результата `ГСП.004.25-АР_ПЗ_на_шаблоне_ИОС2.docx`.
- Для пояснительных записок других разделов, когда пользователь не предоставил отдельный DOCX-образец, допускается использовать рабочую копию файла `assets/templates/Шаблон_ПЗ_рамка_штамп_Кашира_ИОС1_2026_07_20.docx`.
- Не изменяй встроенный шаблон навыка напрямую. Всегда копируй его в рабочую папку проекта или `outputs/...`, затем заменяй содержимое, сохраняя секции, поля страницы, рамки, штампы, колонтитулы, стили, изображения и разрывы страниц.
- При создании листов с рамкой/штампом на основе шаблона сначала проверь, какой тип листа нужен: титульный/содержание/текстовый лист/лист с основной надписью. Используй ближайший существующий лист шаблона как основу и не пересобирай рамку вручную, если её можно сохранить из DOCX.
- При переносе текстовой части АР удаляй только элементы основной части рабочей копии шаблона, сохраняя ее `sectPr`, связи с колонтитулами и геометрию страницы. Переноси абзацы и таблицы из исходной текстовой части вместе со стилями, свойствами абзацев, формулами и выделением. После сохранения проверь точное совпадение извлеченного текста основной части с источником.

### Шрифт и надписи штампа

- Если пользователь предоставляет DOCX как образец или шаблон, считай его безусловным эталоном штампа. Сохраняй из него семейство и размер шрифта, начертание, межсимвольный интервал, масштабирование, выравнивание, поля ячеек, высоты строк, ширины столбцов, рамки, секции и колонтитулы. Не применяй поверх эталона универсальные кегли или другую гарнитуру.
- Переноси текстовую часть в рабочую копию пользовательского шаблона, а не переносить штамп из другого документа в текстовую часть. Меняй в штампе только проектные значения: обозначение, фамилии, даты, стадию, номера и количество листов.
- При замене значений сохраняй существующие `w:rPr` и свойства абзацев. Заменяй текст внутри имеющихся `w:t`; не используй `cell.text` и не пересобирай ячейку, если это уничтожает форматирование эталона.
- Не подбирай шрифт и размеры по скриншоту, когда доступен исходный DOCX-эталон. Встроенный шаблон навыка и технический шрифт применяй только при отсутствии пользовательского Word-шаблона.
- После рендера отдельно проверь в увеличенном масштабе: обозначение документа, фамилии, должности, даты, подписи, `Стадия`, `Лист`, `Листов`, номер листа и боковые надписи. Не допускай обрезки букв, переноса фамилий, наложений на линии и подмены шрифта LibreOffice.

- Сохраняй секции, поля страницы, рамки, штампы, колонтитулы, изображения и разрывы страниц исходного документа.
- Применяй локальные правки; не перестраивай стили и верстку всего документа.
- Если пользователь просит выделить изменения желтым, применяй желтое выделение текста ко всем новым и замененным фрагментам. В добавленных таблицах выделяй текст ячеек, а не закрашивай таблицу целиком, если не указано иное.
- При замене абзаца сохраняй его стиль и свойства абзаца.
- Для баланса используй компактную таблицу только когда она действительно требуется замечанием.
- После редактирования проверь, что исправленный текст находится под правильным подпунктом Положения № 87, а не в соседнем разделе.

## PDF Handling

When source documents are PDFs:

- Use a PDF text extractor for navigation and page-by-page review.
- Use rendered page images for visual verification of edited pages.
- For PDF-only updates, insert new pages rather than overwriting dense existing pages unless there is clear blank space.
- Keep a local notes file during work if many extracted facts must be reconciled.

## Verification

On Windows, render through the packaged `documents/render_docx.py` helper. Do not concatenate `file://` with a Windows profile path when invoking LibreOffice directly: `file://C:\\...` is invalid and may produce a false `bootstrap.ini is corrupt` dialog. Use a unique profile and convert it with Python `Path(profile).resolve().as_uri()` so the value is `file:///C:/...`.

1. Извлеки текст итогового документа и проверь наличие всех внесенных значений и отсутствие заменяемых ошибочных формулировок.
2. Отрендери весь DOCX, а не только измененные страницы.
3. Визуально проверь каждую страницу: рамку, штамп, номер листа, переносы, таблицы, выделение и отсутствие наложений.
4. Дополнительно просмотри измененные страницы в повышенном масштабе.
5. Если штатный рендерер не находит LibreOffice, но установлен Microsoft Word, экспортируй копию в PDF через Word COM `ExportAsFixedFormat`, затем растрируй PDF и выполни ту же визуальную проверку.
6. В финальном ответе дай ссылку только на итоговый DOCX и кратко сообщи, что исходник сохранен.
